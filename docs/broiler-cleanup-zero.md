Clean Up may post a zero-quantity line when the current active cycle has no remaining stock in any of its placement batches and its latest positive inventory movement is an OUT from a posted Harvest & Delivery document belonging to the same farm. Consolidated and original placement batches are supported. An empty balance alone, a draft harvest, a different farm's harvest, negative stock, or mortality that consumes the last birds does not qualify. A verified harvest-emptied cycle qualifies even without mortality-age data; positive-quantity cleanup retains the existing age requirement.

`get_harvest_emptied_cleanup_batches` supplies the form and the posting trigger with the same persisted evidence. The post trigger serializes with the existing Harvest posting lock and checks the selected farm, building, item and batch again. Zero cleanup closes the flock card and inserts a `BR_CLEANUP` OUT inventory posting with `qty = 0` for each selected item/building/batch. Identical retries do not duplicate it. Positive cleanup and variance keep their existing posting behavior. The Building dropdown is enabled for editable drafts, and Add Lines allows manual building selection.

The shared `brCleanup` repository saves through the SECURITY INVOKER transaction RPC. It resolves farm snapshots from `public.farms`, retains table RLS and grants, and atomically saves the header, lines, posting, cycle closure and outbox event. The existing number-based draft recovery now happens inside that transaction. Identical request retries return the saved result.

Notification contract: module `BR_CLEANUP`; events `BR_CLEANUP_POSTED` and `BR_CLEANUP_EDITED`; routing `document` using persisted `br_cleanup.farm_id`, which references `public.farms(id)`. The RPC increments `notification_revision` after the complete action and `enqueue_br_cleanup_event` writes the central outbox in the same transaction. Dedupe identity is `event key:document ID:revision`; a request fingerprint suppresses identical retries. Failed operations roll back events. The dispatcher verifies source/farm identity, then resolves active rules and recipients centrally; no matching rule produces no delivery. Clean Up exposes draft saves/edits and posting, but no supported Void action, so no Void event is registered. Rule activation stays disabled pending target deployment and verification.

Validation: focused ESLint and full TypeScript; disposable PostgreSQL tests use the actual cleanup posting functions, new RPCs and centralized dispatcher. They cover zero harvest, mortality-only depletion, draft/wrong-farm harvests, residual/negative stock, last-movement checks, original/consolidated batches, harvest closeout without mortality age, positive-quantity age enforcement, zero-posting persistence and retry deduplication, positive variance, atomic rollback, retry deduplication, no-rule dispatch, permission/farm-matched delivery and missing-farm rejection. These tests do not establish production RLS or target Supabase deployment.
