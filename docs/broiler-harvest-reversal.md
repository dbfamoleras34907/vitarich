# Broiler Harvest & Delivery reversal

Cross-cycle origin correction: consolidated `DOC:F<farm>:B<building>:<cycle>` batches identify their own cycle explicitly. A later cycle's origin rows may refer to an earlier consolidated batch; those references must not make the earlier cleanup a blocker for the later harvest. Origin fallback now applies only to noncanonical legacy batches, both when finding the original harvest cycle and when checking cleanup. Read-only diagnosis confirmed this case for farm 61/building 6: cycle 2 contained origin `DOC:F61:B6:1`, incorrectly matching cycle 1's posted cleanup. The corrected regression allows cycle 2's harvest reversal after its own cleanup is voided while cycle 1's cleanup remains Posted. Reapply the updated `reverse_br_delivery_transaction.sql` to deploy this correction.

Posted Harvest & Delivery documents expose **Options (…) → Reverse**. The shared Broiler reversal dialog requires `/brd/dr/void` (`conVoid`) and a trimmed reason of 1–1000 characters. Cleanup's existing reversal UI and business rules are preserved.

The confirmed scope is the building's current active cycle only. A **Posted** Clean Up in the same farm/building/cycle blocks reversal. Draft and voided cleanup do not block it. Other later movements within the active cycle do not block reversal. A closed or superseded cycle is rejected. For multiple buildings/batches, every allocation must qualify or the complete reversal rolls back.

`reverse_br_delivery_transaction` restores each original `BR_DELIVERY` OUT as an exact `BR_DELIVERY_REVERSAL` IN, preserving quantity, item, warehouse, batch and references. `delivery_reverses_posting_id` is a unique FK to the original posting; a validation trigger rejects mismatched reversing rows. The original harvest, lines and ledger rows remain. The header stores internal status `Cancelled` (displayed as **Void**), `reversed_at`, `reversed_by`, and `reversal_reason`. Harvest reversal does not close or reopen cycles. The cleanup must be reversed first when it closed the cycle.

The SECURITY DEFINER RPC checks authentication, active user, Void permission, Broiler FMS, active numeric farm assignment, and the canonical `br_delivery.farm_id` relationship to `public.farms`. Super Admin retains the existing permission/assignment bypass. Dependency reads run with full visibility to avoid missing other users' cleanup rows through RLS. Only authenticated callers may execute it. Advisory/table locks serialize eligibility checks and reversal against cleanup/harvest writers. Identical reversal retries return the persisted reversed result without another ledger entry or event.

Notification audit: module `BR_DELIVERY`, events `BR_DELIVERY_POSTED`, `BR_DELIVERY_EDITED`, `BR_DELIVERY_VOIDED`. Post/Edit still complete in `save_br_delivery_transaction`; Void completes in `reverse_br_delivery_transaction`. Each increments `notification_revision` after the successful action, and `enqueue_br_delivery_event` writes the centralized transactional outbox. Dedupe is `event key:document ID:revision`; unchanged draft edits do not increment revision, and already-reversed retries do not mutate. All events use `document` routing from persisted `br_delivery.farm_id`, never the user's default farm. The dispatcher verifies source/farm identity, rejects missing/mismatched farm IDs, applies active rules and recipient View/farm permissions, and safely creates no delivery when no rule matches. Failed mutations roll back events and inventory. Rule activation remains disabled pending target deployment and verification.
